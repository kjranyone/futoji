> 目的: MusicBook の「紙面検出」をさらに高精度化する、および将来の機能拡張
> (文字起こし / 楽譜認識など) に使える、**MIT・Apache-2.0 等の商用寛容ライセンス**で
> スマホ上で軽量に動く画像認識モデルとランタイムの選定記録。
> 調査日: 2026-09-24

## 1. 結論 (先に推奨)

## 2. 現状の実装と位置づけ

本アプリの紙面検出は現状 **OpenCV 等に依存しない純 Dart 実装**
(`lib/services/detector.dart`: 大津二値化 → 最大白連結成分 → 凸包 → 最大面積四角形)。
画像サイズ 320px 幅で数 ms 〜 数十 ms と十分軽量で、**明るい紙 × 暗い背景**では高精度。

ML モデルを入れる価値があるケース:

- 白い机の上の白い紙など、**輝度コントラストに頼れない場面**
- 紙が画面端に切れている/複数の紙がある場面
- 影や照明ムラで二値化が崩れる場面

→ セグメンテーション or 検出モデルで「紙領域」をロバストに推定し、
その後処理 (凸包→最大面積四角形) は現行実装を再利用するのが最小変更。

## 5. 統合手順スケッチ (ONNX + flutter_onnxruntime)

1. **学習** (PC 側): 合成データ (白紙 A4 をランダム台形投影 + 背景写真合成) で
   YOLOX-nano に「紙」1 クラスを学習。
2. **変換**: `torch.onnx.export` → `onnxruntime.quantization.quantize_dynamic` で int8 化 (≈1/4 サイズ)。
3. **組込み**:
   ```yaml
   dependencies:
     flutter_onnxruntime: ^x.y.z   # MIT
   ```
   - モデルは `assets/models/paper_quad.onnx` として同梱 (または初回起動時にダウンロード)。
4. **推論**: 検出用に 320px に縮小したビットマップ → `OnnxRuntime.createSession` →
   出力ボックス/コーナーを現行 `_orderCorners`/`_padCorners` に渡す。
5. **フォールバック**: 推論失敗・低信頼度時は現行の純 Dart ヒューリスティックへ。
   (実装済みの `DocumentDetector.detect` はフォールバック経路としてそのまま残す)

## 6a-2. 実装済み: 自前学習の紙面セグメンテーション (2026-09-25)

「紙を検出する寛容ライセンスの学習済み重みは存在しない」(§4) ため、**合成データで自前学習した重み**を採用した。

- 構成: TinyUNet (386k パラメータ / fp32 1.5MB) — 入力 グレースケール 256x256、出力 紙マスク
- 学習データ: ホモグラフィ合成を無限生成 (`tools/train_paper_net.py`)。
  照明ムラ / 白い机 (明背景) / ドロップシャドウ / 譜線テクスチャ / 枠外はみ出し / センサノイズを含む
- 学習: BCE、Adam、CPU (8スレッド) で 1500 step 約40分。合成検証 IoU は学習ログ参照
- 推論: flutter_onnxruntime (MIT) + ONNX Runtime。実機 1 回 50〜150ms (初回はウォームアップあり)
- 後処理: マスク → 既存の純 Dart 検出器 (`detectLuminance`) で連結成分→凸包→四角形
- フォールバック: モデル不在/推論失敗/マスク不成立時は大津ベースのヒューリスティックへ (精度劣化なしの安全設計)
- 改善ループ: アプリの四隅手修正 (実写+正解) を将来のファインチューニングデータにできる

## 6a-3. 実写データの収集と評価 (2026-09-28)

合成データ・生成画像・BiRefNet 擬似ラベルでは実写での精度が測れないため、
アプリの手修正を正解として貯め、アプリと同一の推論経路で評価する。

**収集** (アプリ)
- ホーム右上メニュー「検出改善用に切り抜き結果を保存」を ON にする (既定 OFF、設定は Hive に保存)
- 切り抜き画面で確定するたびに、表示していた正立画像 (長辺 1000px) と四隅を保存
  (`lib/services/training_capture.dart`)。形式は `<id>.jpg` + `<id>.json` (`QuadLabel`)
  - `corners`: 確定した四隅 (正解) / `predicted`: そのときのモデル出力 (未検出は null) / `edited`: 手で動かしたか
- 取り出し (Android):
  `adb pull /sdcard/Android/data/com.kjranyone.mymusicbook/files/training_captures training_data/eval`

**評価** (PC)
```
pwsh tools/setup_ort_windows.ps1              # 初回のみ ORT 1.20 (MIT) を tools/ort/ へ
flutter test test/paper_net_eval_test.dart     # training_data/eval を評価
```
- 推論は `OrtSessionBundle.detectPaperQuad` をそのまま使う (前処理・穴埋め・四角形推定までアプリと同一)
- 指標: 角誤差 (対応角の距離 / 画像対角線, 4 角平均)、四角形 IoU、成功率 @1% / 2% / 5%、検出率
- 出力: `build/paper_eval/report.md`, `summary.json`, 正解 (緑) / 予測 (赤) のオーバーレイ画像
- 環境変数 `PAPER_EVAL_DIR` / `PAPER_MODEL` / `ORT_DYLIB` / `PAPER_EVAL_OUT` で切り替え可能
  (新モデルの比較は `PAPER_MODEL` を差し替えて同じデータで回す)

注意: `detectLuminance` は四角形を外側へ短辺比 2% 広げる (`_padCorners`)。
手修正の正解が紙の縁ぴったりなら、この分が誤差の下限として乗る。

## 6a-4. v2 モデル: 貼り付け合成 + 事前学習エンコーダ (2026-09-28)

v1 の精度不足の主因は「学習データと実際の撮影の違い」(生成画像は紙が中央に大きく写った単純な構図) と
「BiRefNet 擬似ラベルの誤り」だった。既存データだけで次のように作り直した。

- ラベル: `tools/prepare_quad_labels.py` で BiRefNet マスクに四角形を当てはめ、
  マスクとの IoU ≥ 0.93 の 100 枚だけ採用 (残りはマスク自体が壊れていた)。マスクは四隅から作る
- データ: `tools/train_paper_net_v2.py` で、紙を四隅で切り出し、実写の散らかった机
  (紙領域を除いた部分) や手続き背景へ、大きさ 4〜70% / 任意回転 / 射影 / はみ出し / 影で貼り付け。
  紙なしサンプル 5%、90 度回転、4:3・16:9 を 256x256 へ縦横比無視で縮小 (アプリと同じ)
- モデル: ImageNet 事前学習済み MobileNetV3-Small (BSD-3) + 軽量 U-Net デコーダ。
  1/2 解像度でロジットを出して 256 へ拡大。約 109 万パラメータ / fp32 4.3MB。
  入出力は v1 と同じ (1x1x256x256 グレー → ロジット) なのでアプリ側は差し替えのみ
- 学習: BCE + Dice, AdamW, 2500 step, batch 16, CPU 約 47 分
- 結果 (2026-09-28 再検証。当初の報告は評価データの漏れがあったため差し替え):
  - **実写・学習に一切未使用** (`training_data/eval_heldout`: 紙あり 4 枚 + 紙なし 8 枚。四隅は目視で手付け。
    紙なし 8 枚のうち 6 枚はほぼ同じ場面で実質 3 場面、紙ありも同じチラシ・同じ机で多様性は低い)。
    アプリと同一経路の Dart ハーネス (`./dev.ps1 eval -Data training_data/eval_heldout`) で:

    | 条件 | モデル | 角誤差中央値 | 平均 IoU | 成功@2% | 紙なし誤検出 |
    |---|---|---|---|---|---|
    | 横 (撮影そのまま) | v1 | 7.07% | 0.74 | 25% | 0/8 |
    | 横 | v2 (pad 0) | 1.46% | 0.94 | 100% | 0/8 |
    | 縦 (90 度回転版 `eval_heldout_rot90`) | v1 | 12.65% | 0.56 | 0% | 1/8 |
    | 縦 | v2 (pad 0) | 1.82% | 0.91 | 50% | 0/8 |

  - 合成テスト (チェックポイント選択に使っていない別シード 256 枚): IoU v1 0.53 → v2 0.98。
    ただし背景素材は学習と共通なので参考値
  - 以前記載した「実写 4 枚で 2.71% → 1.68%」は、背景素材として学習に使った画像での評価
    (かつ BiRefNet 由来の不正確なラベル) だったため撤回
  - 四隅の外側パディング: v2 はマスクが紙の縁に合うため 0.02 → 0 (`DocumentDetector.netCornerPad`)。
    上表は pad 0。pad 0.02 では横 1.80% / 縦 2.20%
  - 紙なし判定しきい値 2% → 5% (`DocumentDetector.minPaperMaskFraction`)
- 実機 (Lenovo TB J716F, profile ビルド, `./dev.ps1 selftest`):
  - モデル読み込み 242ms、推論 105〜120ms (紙なし) / 200〜250ms (紙あり、四角形推定込み)
  - 角誤差は PC ハーネスとほぼ一致 (0.33% / 1.34% / 1.82% / 1.84%。差はデコーダの縮小方式の違い)
  - 切り抜き経路 (メイン isolate) とライブ検出ワーカー (別 isolate) で結果が一致
- 既知の限界: 背景まで完全に一様な人工画像 (単色の机に真っ白な矩形) では検出しない
  (実写の机の上の無地の紙は検出する)。実写の評価データが少なく同じ場面ばかりなので、
  アプリの「検出改善用に切り抜き結果を保存」で多様な場面を集めて `eval_heldout` を増やすこと

再学習: `pwsh` で `uv` 環境 (tools/.venv) を作り、
`tools/.venv/Scripts/python tools/prepare_quad_labels.py` → `tools/.venv/Scripts/python tools/train_paper_net_v2.py --steps 2500 --batch 16 --workers 3`
→ `build/paper_seg_v2.onnx` を `assets/models/paper_seg.onnx` へコピー。

## 6a-5. v4 モデル: 重なった楽譜への対応 (2026-09-28)

実写の評価セット (ラーメンのチラシ 1 種類) では楽譜の場面を測れていなかったため、
学習に未使用の生成写真から難例 13 枚 (重なり 6・折れ 5・普通 2) に四隅を手付けした
(`tools/hard_labels.json` → `training_data/eval_hard`、主指標 IoU)。

- v2 の最大の弱点: **重なった複数枚を 1 枚として塗る** (難例の重なり IoU 0.69〜0.86)
- v3: 合成に「奥に 1〜2 枚 + 手前に主な紙 (正解は手前の 1 枚だけ)」と「主な紙の上に小さな紙
  (正解は隠れた部分を含む主な紙全体)」を追加 → 難例 IoU 0.944。ただし副作用で、色付きチラシを
  色の境目で分割する失敗が実写に出た (eval_heldout_rot90 の fail_upright: IoU 0.63)
- v4 (採用): 紙の内側に色の帯・ブロックを描く合成 (正解は紙全体) を追加して v3 から追加学習

| 評価セット (切り抜き経路 1000px、アプリと同じ端末デコーダ) | v1 | v2 | v4 |
|---|---|---|---|
| 実写・横 (紙あり 4 / 紙なし 8) IoU | 0.707 | 0.937 | 0.932 |
| 実写・縦 (90 度回転) IoU | 0.539 | 0.916 | 0.928 |
| 難例 (楽譜 13) IoU | 0.809 | 0.875 | **0.936** |
| 難例 角誤差中央値 / 成功@5% | 4.34% / 54% | 3.62% / 62% | **2.37% / 100%** |
| 紙なし誤検出 | 0/8 | 0/8 | 0/8 |

評価ハーネスのデコードについて: 当初ハーネスは image パッケージで縮小していたが、アプリは端末の
デコーダ (fast_decode.dart) で縮小するため、折れのある画像などで結果がずれていた (実機の自己診断で発見。
例: hard_0111 PC 1.01% / 実機 3.01%)。ハーネスを decodeWorkImage に揃えた後は、実機の自己診断と
13 枚中 12 枚で角誤差が完全一致 (残り 1 枚も 2.94% / 3.01%)。上表はこの揃えた後の値。
6a-4 以前の表の数値は旧デコードでの値。

実機 (Lenovo TB J716F, v4, `./dev.ps1 selftest`): 実写・難例とも全件完走、切り抜き経路とライブ検出
ワーカー経路の結果は全件一致。モデル読み込み 0.24 秒、推論 0.11〜0.36 秒、保存 1.8〜4.2 秒 (紙あり)。

ライブ検出の入力 (長辺 480px, `PAPER_SIM_STREAM=1`) でも同傾向 (難例 v2 0.871 → v4 0.953)。

後処理の検討 (採用せず、評価ハーネスで切り替え可能):
- エッジ吸着 `snapQuadToEdges` (`PAPER_SNAP=1`): 実写は改善、難例は成功@5% が悪化
- マスクのオープニング `openMask` (`PAPER_OPEN=r`): v3 のはみ出し起因の未検出は救えたが、
  v4 では有無で差がない → `netMaskOpenRadius = 0`

学習: `tools/train_paper_net_v2.py --init-pth build/paper_seg_v3.pth --p-multi 0.3 --p-occluder 0.15
--p-panel 0.35 --steps 1500 --lr 8e-4` (v3 は v2 から `--p-multi 0.35 --p-occluder 0.15 --steps 2000 --lr 1e-3`)。
構造は v2 と同一。v4 の実機での自己診断は完了 (上記)。

残る弱点: 丸まった角・大きな折れ (0143, 0179 など IoU 0.84〜0.87)、評価データの少なさ。

### 角の補正: 辺の直線当てはめ (2026-09-28, 採用)

マスク → 四角形の段階で、凸包を 90 点に間引いてから最大面積の四角形を選んでいたため、角の画素そのものが
落ちて角が内側に寄っていた。加えて画素中心の添字をそのまま ÷w していたので、左上へ 0.5 画素ずれていた。
`DocumentDetector._refineByEdgeFit` で、各辺の中央 80% にある領域の境界画素に直線を全最小二乗で当てはめ
(外れ画素を除いて再当てはめ)、隣り合う直線の交点を角にし、連続座標 (+0.5) で返すようにした。
交点が元の角から短辺の 5% より離れる角は元の値を使う。評価ハーネスでは `PAPER_REFINE=0` で無効化できる。

| v4, 切り抜き経路 | 補正なし | 補正あり |
|---|---|---|
| 実写・横 角誤差中央値 / IoU | 1.81% / 0.932 | **0.76% / 0.956** |
| 実写・縦 角誤差中央値 / IoU / 成功@2% | 1.64% / 0.928 / 50% | **1.37% / 0.936 / 75%** |
| 難例 角誤差中央値 / IoU / 成功@2% | 2.37% / 0.936 / 46% | 2.58% / 0.935 / 38% |
| 紙なし誤検出 | 0/8 | 0/8 |

ライブ検出入力 (`PAPER_SIM_STREAM=1`) では実写・横 1.72% → 0.65%、難例 1.71% → 1.75% (IoU 0.953 → 0.948)。
難例の悪化はほぼ hard_0130 の 1 枚 (1.66% → 2.58%) で、マスクが下に重なった紙の束まで含んでいるため、
補正はマスクの縁に正しく沿った結果として束の外周に寄った。ほかの難例の誤差は、補正の有無によらず
マスクの誤り (角 1 つが 5〜10% ずれる) が支配的で、次の改善はモデル側 (折れ・重なりの学習データ) になる。

## 6a-7. ハードネガティブループと 0.1% 誤検出の到達条件 (2026-10-02)

合成 5,256 組のネガティブを偶奇分割 (奇数=mine/学習、偶数=holdout/評価) し、
`tools/eval_synthetic.py --split holdout` を公式指標にしてハードネガティブループを回した
(v7〜v13、計 7 学習)。ツール一式:
- `tools/mine_hard_negatives.py`: モデルの mine 側 FP を train_real に空マスクで登録
- `tools/add_negative_pool.py` / `add_stripe_negatives.py`: ネガポール生成・取り込み
  (残った FP は縞背景の「枠内の明るい矩形」「白ブロブ」→ 特化合成 240 枚で撲滅)
- `tools/shift_onnx_threshold.py`: 出力閾値を ONNX の bias に焼き込む (アプリ無変更)

結果 (合成 holdout 463 ネガティブ、アプリ相当ゲート、検出率は合成ポジティブ):

| モデル | FP(app) | 検出率 | 実写 heldout det | 実写 rot90 det/Fp | 難例 IoU |
|---|---|---|---|---|---|
| v5 | 9/463 = 1.9% | 98.4% | **100%** | **100% / 0%** | **0.946** |
| v9 (v4+ネガポール) | 1/463 | 98.2% | 100% | 75% / 12% | 0.920 |
| v12 (v11+閾値焼込 1.0) | **0/463 = 0.0%** | 97.6% | 75% | 75% / 0% | 0.920 |
| v13 (v5+穏やかネガ) | 4/463 | 98.3% | 75% | 75% / 0% | 0.946 |

**結論**: 合成 FP 0% (≤0.1% の目標) は到達可能 (v12)。ただし実写の繊細な正例
(eval_heldout は正例がわずか 4 枚。rot90 の fail_upright が決定境界上にある) を
1 枚ずつ落とす。合成ネガティブには「本物の紙と区別不可能な明るい矩形」が含まれ、
これを 0 にする圧力は実写正例の検出と直接トレードオフ。**現状のボトルネックは
実写データの少なさ**であり、アプリの改善ループ (捕獲→補正→promote→学習) で
実写の正例・ネガ例を増やすまで、合成 FP 0% と実写検出 100% は両立しない。
よって v4 (現行) のまま、v12 は不採用。ツールと手順は再利用可能。

## 6c. AI でくっきり (保存時の AI シャープ化, 2026-10-05)

設定 → 画質 →「AI でくっきり」(既定 OFF)。補正後の紙面を x4 超解像モデルに
「1/2 に縮小 → x4 → 元の大きさ (2x2 平均)」で通し、ぼけ・ノイズ・紙の地模様を取る。
実装は `lib/services/ai_sharpen.dart`、評価は `tools/sr_eval.py` / `tools/sr_quantize.py`。

**モデル**: Real-ESRGAN `realesr-animevideov3` (BSD-3, SRVGGNetCompact 16 層) を int8 静的量子化
(QDQ・重みチャネル別、実写タイルで較正)。入力 256x256 固定のタイル推論 (重なり 8px・端は反射)。
アセット `assets/models/sr_anime_x4v3_int8_t256.onnx` (666KB)。

| 比較 (HiPad / MT6785) | 1 ページ (1794x2288) | 備考 |
|---|---|---|
| general-x4v3 fp32・1/2 縮小・ORT 既定 | 130 秒 | 初版。小さい文字も読める |
| animevideov3 fp32・1/4 縮小・XNNPACK 8 | 12 秒 | **小さい文字が別の字形に崩れる** (「23:00」→「2S:00」) |
| animevideov3 **int8**・1/2 縮小・CPU 8 スレッド (カメラ稼働中) | 16 秒 | |
| 同上・保存中はカメラのプレビュー/フレーム配信を停止 | **9.3 秒** | 採用 |

- 1/4 縮小は情報が足りず、紙が小さく写った撮影で文字が作り変えられる。1/2 が下限
- 汎用版 (general) は文字・音符の周りに白い縁取りが出る。線画向け (anime) は出ない
- int8 は fp32 比 PSNR 約 38dB で、文字・音符の見た目は同じ。速度は約 2.7 倍
  (int8 は XNNPACK だと遅く、標準 CPU 実行が速い)。fp16 は速くならない
- 推論は実機でカメラのプレビュー・フレーム配信と CPU を取り合い約 2 倍遅くなるため、
  AI 仕上げ中はカメラを止める (`CameraScreen._savePage`)
- 既知の限界: QR コードのような細かい図形は AI が迷路状に描き直す (読めなくなる)。
  楽譜・文字は 1/2 縮小なら崩れない
- 速度の比較は 自己診断 (設定で許可) の `selftest/AIBENCH` で、selftest/ に置いた候補モデル
  (`*_t256.onnx` などファイル名のタイル寸法) と ORT 設定を総当たりで測れる

## 6d. 紙面の湾曲補正 (五線ベース, 2026-10-08 試作)

台形補正 (`warper.dart` のホモグラフィ) は平面の傾きしか直せず、本のノド付近の反りは残る。
楽譜は「五線は本来まっすぐ水平・等間隔」という強い手がかりがあるため、学習モデルを使わず
古典的な手法で縦方向の変位場を推定する。試作は `tools/dewarp_staff.py`。

- 学習済みの補正モデル (DocTr++ / UVDoc / DewarpNet) は学習データ Doc3D の利用条件と
  重みのライセンスの確認が必要で、文字文書で学習されているため採用しない。
- 手順: 縦の短冊 (幅 ~W/24) ごとに傾きを振って横投影 → 「sp 間隔で 5 本そろい、間と
  外側 (±3 間隔) は空いている」櫛として五線を検出 → 短冊間をつないで五線ごとの点列に
  → D(x, y) = Σ c_ab x^a y^b (a=1..6, b=0..2) を各線のまっすぐな高さと交互に最小二乗
  → `y_src = y + D` で再サンプリング (2 回反復し、写像を合成して 1 回だけ再サンプリング)。
- 安全策: 五線が 5 本未満なら補正しない / 線が縦の狭い範囲だけなら x のみの変位 /
  変位がページ高さの 12% を超えたら破棄 / 補正後に検出し直して曲がりが 2 割以上
  減らなければ破棄。表の罫線 (等間隔の横線) は外側が空いていない条件で大半を落とす。
- 評価 (`eval_hard` の楽譜 13 枚の台形補正後 + それに既知の湾曲をかけた合成 26 枚、
  指標 = 線ごとの当てはめ曲線の上下幅の中央値):

  | | 件数 | 補正した | 補正前 | 補正後 (中央値 / 最大) |
  |---|---|---|---|---|
  | 実写 | 13 | 13 | 23.1px | 1.5px / 5.8px |
  | 合成 (ノド反り) | 26 | 24 | 27.1px | 1.4px / 8.2px |

  幅 1200px。補正を見送った 2 件は安全策で恒等に戻ったもの (壊してはいない)。
- 未対応: ノド付近の横方向の縮み (縦の変位のみ推定)、五線のないページ。
- 処理時間: Python (numpy, 素朴なループ) で 1 枚約 3 秒。

  保存全体は中央値 2.4 秒 (補正なしなら約 1.1 秒)。PC (JIT) は約 0.27 秒。

### 並列化の検討と追加の高速化 (2026-10-08)

実機の SoC は Cortex-A76 x2 (2.05GHz) + Cortex-A55 x6 (2.0GHz)。

- 検出を「前処理 (二値化) / 短冊の走査 / つなぎ込み」に分け、短冊の走査を
  `Isolate.run` で N 本に分ける実装を入れた (`StaffDewarp.detectLinesParallel`)。
  結果は 1 本で走査したときと完全に一致する (単体テストで確認)。
- しかし実機では分けるほど遅かった (推定のみ、13 枚の目安):
  1 本 約 0.75 秒 / 2 本 約 1.1 秒 / 4 本 約 1.4 秒 / 6・8 本はさらに遅い。
  isolate の起動は 5 本で 2〜3ms と安いが、2MB を渡すと 1 本あたり約 20ms のコピーになり、
  検出 3 回 x 本数ぶん積み上がる。省電力コアに回った分の待ちも出る。→ 既定は 1 本
  (`--dart-define=DEWARP_WORKERS=n` で計測用に上書き可)。
- 代わりに計算量を減らした:
  - 傾き探索で短冊を 5 列ずつ先に足しておき、傾きごとには 10 個のまとまりをずらして足す
    (まとまり内のずれの差は最大 0.4px)。品質は変わらず (実写 1.2px / 合成 1.5px)。
  - 二値化の積分画像 (Int64, 1 回の検出で約 16MB) をやめ、列ごとの縦の窓の和 + 行内の累積和に。
    結果は列ごとの並びで直接書き、転置を省いた。
- 結果: 保存処理の `iso_dewarp` は中央値 1.32 → 0.93 秒、保存全体は 2.38 → 2.10 秒。
- 残りの大きな工程だった台形補正 (`warpPerspectiveRgb`) を単一スレッドのまま高速化した:
  画素ごとの `Offset` の生成と関数呼び出しをやめ、行の中では射影の分子・分母を足し算で進める。
  双一次補間は整数の重み (2^-11 刻み)。検出用には輝度を直接出す `warpPerspectiveGray` を使う。
  素直な実装との差は ±1 以内 (test/warper_test.dart)。評価の品質は変わらず。
  実機 (eval_hard 13 枚): `iso_warp` 中央値 0.21 → 0.10 秒、`iso_dewarp` 0.93 → 0.68 秒、
  保存全体 2.10 → 1.71 秒。評価画像は元写真が小さい (750x1000) ので、実際の撮影
  (長辺 2600px) では台形補正の短縮幅はもっと大きいはず。

### 保存の後段 (BMP 化・サムネイル・WebP) の高速化 (2026-10-08)

eval_hard は元写真が小さいので、実寸の撮影 (eval_heldout, 4160x3120 → 出力 約 2600x1950) で測った。
紙が全面に写る 8 枚の中央値付近:

| 工程 | 前 | 後 |
|---|---|---|
| BMP 化 (`iso_bmp`) | 0.20 秒 | 0.037 秒 |
| サムネイル縮小 (`iso_thumb`) | 0.39 秒 | 0.045 秒 |
| WebP 変換 (`webp`, 本体 + サムネイル) | 約 1.0 秒 | 約 0.9 秒 |

- BMP は img.Image を経ずに RGB のバイト列から直接書き、サムネイルは整数の面積平均で縮小する
  (`lib/services/raster.dart`)。
- flutter_image_compress は Android 側の 8 スレッドのプールで処理するので、本体とサムネイルを
  同時に投げる (サムネイルは本体の陰で終わる)。
- WebP 変換 0.9 秒の内訳: 同じ BMP (11MB) を JPEG にすると約 0.28 秒、1x1 の往復は 2ms。
  転送 + BMP デコードは 0.28 秒未満で、**WebP のエンコード自体が約 0.6〜0.7 秒**。
  Android の `Bitmap.compress(WEBP)` はエンコーダの設定 (method やスレッド) を変えられないので、
  これ以上は (a) 保存を裏で順に流してシャッターを待たせない、(b) libwebp を FFI で同梱して
  速い method + マルチスレッドで符号化する、(c) JPEG にする (速いがファイルは大きい) のどれか。
- 既知の誤検出: 表の罫線の一部を五線 1 段と見なすことがある (hard_0070)。その場合も
  x だけの変位になり、行がわずかに水平にそろう程度で壊れない。
- 次: クロップ画面に辺の中点ハンドル (手動の曲線補正, Coons パッチ) を足す。
  五線・段の検出結果は半ページめくり (段単位の送り) にも流用できる。

楽譜の音符認識 (OMR) は 2026-10-08 時点でも引き続きスコープ外: 寛容ライセンスで
モバイルに載る実用精度の実装がなく、MusicXML の表示・再生・修正 UI まで要るため。
